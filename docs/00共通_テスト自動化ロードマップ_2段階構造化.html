01

出発点 ― 1年分の Redmine 工数分析

「どこを改善すれば効くか」を、過去1年(2025/03–2026/02)の Redmine 工数を全カテゴリに分類して特定した。本プロジェクトが担うのは ② と ③ の2領域。

本PJが担うのは ②テストケース作成（第1弾） と ③条件作成＝J条件/詳細設計（第2弾）。①は別PJ（着手しない）。③は未着手で計上0.4%だが、設計判断が暗黙化しているだけで形式知化の余地が大きい。

02

この仕組みとは ― 歩掛JSON差分からのテストケース生成

歩掛が改定されると、歩掛JSONの旧版と新版の差分から「変わった条件・フロー」を特定し、システムテスト用のテストケースを自動で生成する。②テストケース作成の重量級工数（1件30〜60h）を圧縮するために作ったエンジン。

STEP 1

差分を抽出

旧JSON ↔ 新JSON を比較し、質問・選択肢・計算式・フローの変更点を洗い出す。

STEP 2

影響範囲を特定

変更が効くフロー・条件を辿り、テストすべき分岐パターンに絞り込む。

STEP 3

テストケースを生成

分岐ごとの入力条件＋積算シミュレートの期待値を、テストケースとして出力。

エンジンは構築フェーズを完了済み（合格21工種・回帰34工種で完全一致）。技術的には動く ― だからこそ「これをどう使うか」を運用目線で見直したのが次章。

03

なぜ路線を変えるのか ― 運用目線のフィードバック

エンジンは技術的には完成した。しかし運用メンバーに仕組みを説明したところ、「このままTC生成を主役にすると品質保証の構造が崩れる」という本質的な指摘が出た。それが今回の路線変更の起点。

問題 01

テストファーストが崩れる

現エンジンは「成果物(歩掛JSON)が正しい前提」でTCを生成する。テストが実装から導出される循環構造になり、実装ミスをテストで捕まえられない。

→ 成果物正前提の循環
問題 02

詳細設計が書ききれていない

修正方針はざっとしか書かれず、品質が実装者のスキルに依存している。設計判断が形式知化されていない。

→ 実装者スキル依存
問題 03

人手のTCを止められない

結局いまは Redmine の修正方針＋人が書くテストケースで品質を担保している。だから人手TCを廃止できず、自動化の効果が頭打ち＝リスク。

→ 二重運用が残る
気づき

目指すのは「TC生成の全自動化」ではない。テストファーストの構造を壊さずに本仕組みを活かすこと。人がテストを書く役割は残し、エンジンは “叩き台づくり” と “乖離・合否チェック” に役割を移す。

04

発想の転換 ― テストケースを「何から」作るか

変えるのは入力。「修正後JSON から作る」のをやめ、「商品JSON ＋ 改定内容 から作る」へ。これがロードマップ変更の核心。

これまで（完成品ありき）

「修正後JSON」から TC を生成

改定が終わった“完成品”のJSONを読む

その動作をなぞって TC を作る

→ 成果物が正しい前提＝テストが後追い

→
第1弾（テストファースト）

「商品JSON ＋ 改定内容」から TC を作る

商品JSON（改定前の既存版）を土台にする

そこへ改定内容を盛り込んで TC を組む（人が編集）

→ 完成品を待たずにテスト準備＝テストファースト維持

エンジンの役回り：商品JSONから TCの叩き台 を出す → 人が改定内容を盛り込む → 出来た TC を改定後JSONと突き合わせて 検証（乖離・合否）（詳細は次章）。

② テストケース作成を運用に乗せる

現ロジックをそのまま活かす。新規開発は「乖離チェックの入力差し替え」1点。

  1. 商品JSON（改定前の既存版）を1つ投入 → 叩き台TCを生成現ロジック新規工種扱いでテストパターンを生成。JSONを1本入れるだけで出力。
  2. 人が加工して改定後TCを作る人増えた条件選択を挿入するなど。テストを書く主体は人＝テストファースト維持。
  3. 乖離チェックに「人作成TC」を入力新規人作成TCを正として改定後JSONと突き合わせ（合否＋未カバー差分）。修正方針があれば補助ヒントに併用、無ければTC単独で成立。
  4. 積算シミュレートで合否判定正解振る舞い＝改定後TC。合否判定の実現性が高い。

対称性
