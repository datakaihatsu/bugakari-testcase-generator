# アイデア：官公庁設計書との突き合わせによる仕様適合性検証
# 作成: 2026-05-21

---

## このアイデアが解決する課題

`課題_仕様適合性テストの限界.md` で指摘した根本問題：

> **「JSONは実装結果であり、テストの真実の源泉をJSONに置く限り、  
> 実装漏れ・オーバースペック・係数ミスは検出できない」**

この問題の解として、**官公庁が公開する「設計書」を外部の真実の源泉として活用する**。

---

## アイデアの概要

官公庁は積算結果を「設計書」と呼ばれる表形式で公開している。  
設計書には **条件（入力）と積算結果（出力）** が記載されており、  
これは弊社の積算シミュレートが一致すべき正解データである。

```
【現在のテストの構造】

  JSON（実装）→ テストケース生成 → 積算ソフトで検証
      ↑
  テストの正解もJSONから来ている（循環）

【提案する構造】

  官公庁設計書（正解）
       ↓ 条件・結果を抽出
  突き合わせテーブル
       ↑ 条件・期待値を照合
  テストケースCSV（本日作成）← JSON（実装）
       ↓
  乖離の可視化（何が合っていて何が合っていないか）
```

---

## 突き合わせのイメージ

### 設計書から読み取れるもの

| 設計書の記載 | テストケースCSVの対応列 |
|---|---|
| 工種・施工条件（省庁・施工方法） | グループ情報（治山林道×BH施工） |
| 代価表の種別（10m3単位など） | 代価表当り単位（固定）列 |
| 資材の有無・種類 | 資材計上区分・砕石の種類列 |
| 一般世話役 数量 | 期待：S1 |
| 特殊作業員 数量 | 期待：S2 |
| 普通作業員 数量 | 期待：S3 |
| 砕石 数量 | 期待：S4 |
| 機械 数量 | 期待：S5 |

### 突き合わせ後の状態

```
テストケースCSV（期待値）  vs  設計書（正解値）
─────────────────────────────────────────────
TC-001  S1=0.2 ─── 設計書 S1=0.2  → ✅ 一致
        S2=0.4 ─── 設計書 S2=0.4  → ✅ 一致
        S3=0.9 ─── 設計書 S3=0.85 → ❌ 乖離あり（丸め差？実装ミス？）
        S4=13.0 ── 設計書 S4=13.0 → ✅ 一致
```

乖離が見えた時点で「JSONの実装が基準と合っているか」を初めて議論できる。

---

## 期待される効果

### ① 実装漏れの検出
設計書に条件が存在するのに、テストケースCSVに対応するケースがない  
→ JSONに実装が漏れている可能性がある

### ② オーバースペックの検出
テストケースCSVに条件があるが、設計書に該当ケースが存在しない  
→ JSONに不要な実装が混入している可能性がある

### ③ 係数・歩掛値ミスの検出
テストケースCSVの期待値（JSON由来）と設計書の値が乖離している  
→ 係数の入力ミスや計算式の誤りを発見できる

### ④ エージェント化への橋渡し
設計書を構造化データとして整備できれば、  
「設計書→テストケース自動生成→JSON実装の検証」というパイプラインが実現する

---

## 実現するための前提条件・課題

| 条件 | 現状 | 課題 |
|---|---|---|
| 設計書の入手 | 官公庁が公開している | 都度取得が必要 |
| 設計書の構造化 | PDF・紙ベースが多い | 機械読み取り可能な形式への変換が必要 |
| 条件の対応付け | 手動でマッピングが必要 | 設計書の条件表記と入力列の名寄せが必要 |
| 突き合わせの自動化 | 現状は手作業 | CSVと設計書データを自動照合するツールが必要 |

---

## 短期的な取り組みイメージ（手動版）

自動化前でも、以下の手順で価値を出せる。

1. 今回の工種（裏込砕石工）の設計書を1件入手
2. 設計書の条件と数量値を手動でCSVに転記
3. テストケースCSVの期待値と横並びで比較
4. 乖離があれば原因を調査（丸め差・係数ミス・実装漏れ）

これだけで「JSONが正しいかどうか」を初めて外部基準で確認できる。

---

## 位置づけ

```
現在のテストケースCSV（4件）
  → 「作ったものが壊れていないか」を確認するもの

設計書との突き合わせ
  → 「作るべきものが作られているか」を確認するもの
```

両方が揃って初めて、積算シミュレートの品質を体系的に保証できる。
