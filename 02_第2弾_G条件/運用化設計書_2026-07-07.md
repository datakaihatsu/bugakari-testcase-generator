## 0. 用語

### 目的
運用メンバーが Claude（対話）なしで ①③ を回せる**独立ローカルツール**にする。

## 4. データフロー（運用シナリオ）

```
[① タブ]
  運用者入力: Gaia9キー or 歩掛キー(例 65-14-160-20350 / 160-1351)
    │  locate.KeyMapping → 歩掛キー
    │  locate.find_bugakari_json → 版一覧提示（既定=最新）
    │  運用者が版を確認/選択（改定前=現行リリース版）
    ▼
  build_g(選定JSON) → 20_G条件.csv（内部CSV。回帰の20は不変）
    │  io_xlsx: CSV → xlsx（装飾なし・値のみ＋列幅/フィルタ程度）
    ▼
  ダウンロード: 商品_Gaia入力基準表_<工種>(<単位>).xlsx  ← 画面/ファイル名は運用者向け名称

  ── 運用者がExcelで「改修後」に手編集（選択肢の追加/文字変更/新規条件 等） ──
  ──   → 改修後_Gaia入力基準表_<工種>(<単位>).xlsx として保存                    ──

[③ タブ]  ※投入枠を2つに分ける（ファイル名で判別しない）
  枠A「商品G条件」 : 商品_...xlsx（①出力）
  枠B「改修後G条件」: 改修後_...xlsx（人編集）
    ※改定前JSONは①で特定済みのものをセッションに保持 or 再特定
    │  io_xlsx: 枠A→csv20 / 枠B→csv30（各枠が20/30を決めるので名前依存しない）
    ▼
  run(csv20, csv30, old_json) → step3.0_テストケース_<工種>.csv（内部CSV）
    │  io_xlsx: CSV → xlsx
    ▼
  ダウンロード: テストケース_<工種>.xlsx
```

**運用者向け名称（境界層のみ・内部/回帰は 20/30 のまま）**:
- 20（改定前＝現行リリース版）= **「商品」**。30（改定後＝人編集）= **「改修後」**。
- **③は入力枠を A=商品 / B=改修後 の2つに分離**。どちらの枠に入れたかで 20/30 が確定するため、
  同名2ファイルでも取り違えない（ファイル名依存の運用を廃止）。

**導線設計**: ③の入力=①の出力の人編集版。①実行後、その 20_G条件 と old_json パスを
**セッションに保持**し、③タブ枠Aに「①の結果を引き継ぐ」ボタンを置く（手作業の受け渡しミス防止）。

## 6. ① 詳細設計

### API（service層）
```
service.locate_versions(gaia9_or_key: str) -> {
    "bugakari_keys": [...], "candidates": [{"key","ymd","path","is_latest"}...],
    "chosen": {...} | None, "error": None|str }
service.gen_g(json_path: str) -> {"csv_path", "xlsx_bytes", "log", "g_count", "notes"}
```

### 処理
1. 入力文字列を `KeyMapping.parse_gaia9_key` で判定。数値3/4要素=Gaia9キー→歩掛キー変換。
   `160-1351` 形式（ハイフン2要素）は歩掛キー直接指定として扱う（27には無い分岐＝追加）。
2. `find_bugakari_json` を呼ぶ **前に**、候補一覧（全版）をUIへ返し、既定=最新を選択状態にする。
3. 運用者が版を確定 → `build_g(json_path, out_dir=一時dir)` → CSV → xlsx化して返す。

### 論点
- **歩掛キー直接指定の対応**（Gaia9キーが分からない運用ケース）。→ 追加する。
- **複数歩掛キーがヒット**（1 Gaia9 → 複数歩掛）時のUI。→ キー選択も一覧提示。
- **格納場所が運用者PCで異なる**。→ config.json＋UI設定欄。

## 7. ③ 詳細設計

### API
```
service.gen_tc(xlsx20_bytes, xlsx30_bytes, old_json_path) -> {"csv_path","xlsx_bytes","log"}
```

### 処理
1. `io_xlsx.xlsx_to_gjoken_csv` で 20/30 xlsx → CSV（cp932・セル内改行復元）。
2. `old_json` は①セッション保持値を既定。無ければ①同様にキー特定させる。
3. `run(csv20, csv30, old_json, out_dir=一時dir)` → TC CSV → xlsx化。

`build_g`/`run` の `print` は書き換えない。service層で
`contextlib.redirect_stdout(io.StringIO())` で捕捉し `log` として返す（UIに表示・エラー切り分け用）。

## 8. 境界層（io_xlsx）設計 ― 事故防止が主目的

**なぜxlsxか**: セル内改行入りCSVをExcelで開いて保存すると cp932/引用符で壊れる。G条件は
人が編集して③へ戻す往復があり致命的（継続メモの確定事項）。

### 方針
- **G条件テンプレで列構成を固定**（往復の書式ゆれ対策・第3弾の読み戻しにも効く）。
- 装飾は**最小**（値のみ＋列幅・フィルタ程度）。見栄えでなく事故防止。
- 内部パイプライン・回帰は**CSVのまま**（バイト比較・diff性維持）。xlsx⇔CSVは境界に1枚だけ。

### ライブラリ論点（本日「標準ライブラリのみ」決定との整合）
- xlsx読み書きは**標準ライブラリでは不可**（openpyxl等が必要）。
- 「標準ライブラリのみ」の決定は**Webサーバ部（http.server）**を指す。xlsxは境界の1モジュールに閉じる。
- **推奨**: openpyxl を**この1モジュールに限定して同梱**（zipに whl 同梱 or vendored）。
  Webフレームワーク依存（Flask等）は避けつつ、xlsxは openpyxl を許容する。→ §12で要確認。
- 代替案: xlsx を諦め「タブ区切りをUTF-8 BOM付きで書き出し、Excelは読み取り専用で開く運用」
  → 往復編集の事故防止という当初目的を満たさないため**非推奨**。

## 9. Web UI（http.server・依存ゼロ）

### サーバ
- `http.server.ThreadingHTTPServer` ＋ `BaseHTTPRequestHandler`。
- ルート: `GET /`(index) / `GET /static/*` / `POST /api/locate` / `POST /api/gen_g`
  / `POST /api/gen_tc`（multipart or base64 でxlsx授受）/ `GET /api/config`。
- localhost バインドのみ（`127.0.0.1`）。ポート既定 8765。

### 画面（タブ2枚・SPA）
- **タブ①**: キー入力 → [検索] → 版候補テーブル(ラジオ・既定最新) → [G条件生成] → 「商品_…xlsx」ダウンロード＋ログ。
- **タブ③**: **入力枠を2つに分離** — 枠A「商品G条件」(①結果引継ボタン付き)／枠B「改修後G条件」
  → [TC生成] → 「テストケース_…xlsx」ダウンロード＋ログ。**同名2ファイルでも枠で区別**するため取り違え不可。
- 進捗表示: ③は工種により30秒〜（tc3回帰で21が30秒超の実績）。**非同期＋スピナー**必須。

## 10. 配布方式

- **Python同梱zip ＋ 起動bat**（PyInstaller はAV誤検知・cp932・同梱データの罠で回避）。
- **運用PCへのPythonインストールは前提にしない（推奨）**: zipに **埋め込みPython(python-3.x-embed.zip)** を同梱し、
  batダブルクリックだけで完結（管理者権限・PATH設定・事前インストール不要）。openpyxl も embed に同梱。
  - 難点はzipサイズ（数十MB＋openpyxl）のみ。非エンジニア運用者にはこの容易性が勝る。
  - 代替（既存Python前提）: 配布は軽いが運用者が事前にPython導入＋PATHが必要 → 非推奨。
- zip内容: `python-3.x-embed/` ＋ `webapp/` ＋ `openpyxl`(embed の site-packages に vendor) ＋ 起動bat。
- `起動_運用ツール.bat`: 同梱pythonで `webapp\server.py` 起動→数秒後 `start http://127.0.0.1:8765`。
- 改修頻発期は更新容易性優先（zip差し替えのみ）。安定後にサーバ載せ替え/exe化を再判断。
