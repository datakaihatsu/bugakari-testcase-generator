# 原因報告: ③テストケース生成(改定)で IndexError（鉄枠固定ボルト材料費）

- 報告日: 2026-09-02（協力会社より・実行ログ添付）
- 工種: 鉄枠固定ボルト材料費(組)　歩掛キー **160-1722**（適用 20191001・質問数 5）
- 症状: 添付の 商品/修正後 xlsx で「③テストケース生成(改定)」→ `IndexError: list index out of range`
  （`generate_csv.py _compute_reach_combos` の `default_rows = [rs[0] for _, rs in vary_row_lists]`）。
  「新規歩掛」モードでは生成できる。8/27 に同じ工種で成功した xlsx（#544444）も通る。
- **ローカルで同一エラーを再現済み**（`再現_中間ファイル/` に中間ファイルを保存）。
- 状態: **原因特定済み・修正は未着手**（指示どおり）

## 結論（一文で）

修正後G条件で **条件名を「蓋区分」→「○区分」に変え、選択肢を全部入れ替えた**ため、
ツールが「同じ条件の改名＋選択肢の全削除」と解釈し、**新しい選択肢を追加できずに質問の選択肢が0行**になり、
その質問を vary 軸として展開しようとした箇所で落ちた。

## 入力の違い（成功例 #544444 との比較）

| | 商品（共通） | 8/27 成功例の改修後 | 今回の修正後（失敗） |
|---|---|---|---|
| 条件名 | 蓋区分 | ロックボルト(M-16) の形状 | **○区分** |
| 選択肢 | ①標準蓋 T-20 ②標準蓋 T-25 ③タイル用 ④レンガ用 | ①L=150㎜ ②L=105㎜ | ①ロックボルト　L=150 ②ロックボルト　L=105 |

どちらも「条件を丸ごと差し替え」だが、**条件名の文字の似方**だけが違う。

## 機構（コードで追った結果）

1. **列の対応付け** `gen_tc_from_gjoken.diff_gjoken` → `_best_pairs(cutoff=0.5)`：
   条件名を `SequenceMatcher.ratio` で突き合わせる。
   - 「蓋区分」vs「○区分」= **0.667 ≥ 0.5 → 同じ条件の改名と判定**（3文字中「区分」2文字一致）
   - 「蓋区分」vs「ロックボルト(M-16) の形状」= 0.000 → 別条件（削除列＋新規列）→ 成功例はこちらの経路
2. **選択肢の差分**（改名と判定された列のみ）`_best_pairs(cutoff=0.4)`：
   旧4選択肢と新2選択肢の類似度は最大 0.12 → 対応なし → **削除4件・追加2件**
   （`step1.0_G条件差分レポート.csv` に削除4行が出ており、追加行が無い＝ここで既に追加が消えている訳ではなく、次の3で落ちる）
3. **擬似改定後JSONの合成** `build_pseudo_json` → `_edit_sit`：
   - 追加選択肢は「最も似ている既存選択肢の行を**複製**して作る」方式（複製元 = `標準蓋 T-20` 等）
   - ところが **先に削除を全 sit に適用**（`_edit_sit(data, sit, dels, renames, [])`）してから
     **後で追加**（`_edit_sit(data, sit, [], {}, adds)`）する順序になっている
   - 追加時に複製元の行を探す `rows_with(src_lbl)` が **削除済みで見つからず `continue`（無言でスキップ）**
   - 結果: 質問2「○区分」の `SitRows` は固定行 1〜3 だけ、選択肢行 4〜7 は消え、新選択肢は 0 行
     （`再現_中間ファイル/_擬似改定後.json` で確認できる）
4. **TC生成** `generate_csv.generate`：
   計画（`step2.0_テスト計画.csv`）は「○区分 = vary（選択肢テキスト変更／選択肢削除）」。
   `_get_axis_rows` は `Visible かつ not IsFixed` の行を選択肢とするので **空リスト**。
   `_compute_reach_combos` の `rs[0]` で `IndexError`。

つまり **「選択肢が1つも共通しない改名列」** という入力パターンで、
「削除→追加（複製）」の順序依存により追加が成立しない、という設計上の穴。
成功例が通ったのは、条件名が似ていなかったため偶然この経路に入らなかっただけ。

## 影響範囲

- 発生条件: 修正後G条件で (a) 条件名が旧名と**似ている**（ratio ≥ 0.5）かつ (b) 選択肢が**旧と1つも対応しない**。
  「○区分」「△区分」のような**仮の名前**を付けて中身を全部書き換えると踏みやすい。
- 選択肢が1つでも旧と対応（類似度 ≥ 0.4）していれば、その行が複製元として残るので発生しない。
- 「新規歩掛」モードは改定前との差分を取らないので無関係（報告どおり動く）。

## 修正の選択肢（未実施・要判断）

1. **追加を削除より先に適用する**（`build_pseudo_json` の順序変更）: 複製元が残っている状態で追加してから削除。
   最小変更・本質対処。既存工種への影響は回帰で確認要（追加行の RowID 採番順が変わり得る）。
2. 改名列で選択肢が**全滅**する場合は「削除列＋新規列」として扱う（成功例と同じ経路に寄せる）。
   意味的にも自然（名前が似ていても中身が別物なら別条件）。
3. 防御: `_edit_sit` で複製元が見つからないときに無言で `continue` せず、
   利用者向けエラー「条件『○区分』の新しい選択肢を作れませんでした（旧選択肢と対応が取れません）」を返す。
   1 or 2 と併用するのが望ましい（黙って0行になるのを止める）。

推奨: **2 ＋ 3**。1 だけだと「蓋の選択肢行を複製して名前だけ書き換えた行」が新選択肢になり、
行の属性（変数設定・既定行など）が旧選択肢のものを引き継ぐ点が成功例と食い違う。

## 利用者向けの当面の回避策

修正後G条件の条件名を、旧名と似ていない**本来の名前**（例:「ロックボルトの形状」）にする。
8/27 に成功した xlsx はまさにその形。

## 対処（合意 2026-09-02: V1 ＋ 案1 ＋ 案3）

判断の経緯（ユーザ決定）:
- 文字だけでは「同じ物の名前直し」と「別物への置き換え」は判別できない。Gaia 側は選択肢上書きで実装される
  ため、TC は上書き前提になる。**テスト漏れより過剰の方が安全**（不要な TC は人が削れる）。
- よって **条件名は完全一致のみ同じ条件（V1）**。名前が変わった列は別条件（削除列＋新規列）として全選択肢を網羅する。
  選択肢の突合（類似度 0.4）は現行のまま（V2＝選択肢まで完全一致は、12 重建設機械分解組立 3→19 行などの増え方を見て別途判断）。
- 併せて **案1**（擬似JSON合成の適用順を「追加→削除・文字変更」に）で A③（同名・選択肢全入替）も通し、
  **案3**（追加できなかった選択肢が残れば `GjokenApplyError` で利用者向けに止める）で「黙って 0 行→IndexError」を塞ぐ。

- `gen_tc_from_gjoken.diff_gjoken`: 条件名の対応付けを完全一致のみに（`_best_pairs(cutoff=0.5)`・接頭辞ボーナス B-7 を条件名には使わない）
