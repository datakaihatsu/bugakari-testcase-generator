# 不具合: 組合せ上限の縮退で G条件表の(注)が誤る（43 捨石本均し・荒均し／潜水士船）

- 発見日: 2026-09-02（v1.2.0 リリース時に E2E回帰 `run_regression_tc3.py` で 43 だけ DIFF）
- 対象: 43_610827 捨石本均し・荒均し(水中)、捨石本均し・荒均し(陸上)
  Gaia9キー **65-3-32-20077** / 歩掛キー 32-5251 / 改定前 20250401 → 改定後 20260401
- 混入版: v1.1.2（2026-08-31・組合せ爆発フリーズ対策）
- 対処版: **v1.2.1**（2026-09-02）

## 症状

20_G条件.csv / 30_G条件.csv の(注)ブロックだけが変わる（50行→53行）。TC は不変。
例: 注4「G2=②荒均し済(±50cm)」に G13「目潰石の計上」・G15「100m2当り目潰石使用量」が
「入力不要」として追加されるが、全組合せではこれらは必要。

## 切り分け（実証）

| 実験 | 結果 |
|---|---|
| v1.2.0 の変更を stash した HEAD で 43 を再実行 | 同じ DIFF → v1.2.0 とは無関係 |
| 上限を外して全組合せ(1,200件)で再生成 | **ベースラインとバイト完全一致**、所要 3.2〜10.5 秒 |
| `_build_combos` の呼び出し追跡 | gen(新規工種モード)=600件で全組合せ、網羅性補完の gen2=1,200件で縮退(15件)→ 劣化チェック通過で gen2 の注が採用 |

## 原因

注の導出（`gen_gjoken.py` `_derive_glist` 内）は
「Gx=v の全 combo で Gy が '-' なら『Gx=v なら Gy 不要』」という **combo 列からの帰納**。
縮退（基準+1軸ずつ変更）では各非基準選択肢が combo 1件にしか現れないため、
他の非基準選択肢との組合せでのみ到達する Gy が観測されず、1サンプルで「不要」と断定する。
縮退は列・選択肢の網羅を保つ設計なので、網羅性補完の劣化チェック（列・選択肢の喪失のみ検査）では
検知できない。

## 計測

- 回帰35工種 × 改定前/改定後 = 70回: 縮退発動は 43 の2回のみ → `計測_35工種の縮退発動状況.csv`
- DB 53,267工種から無作為500: 縮退 24件(4.8%) / 3,000超 16件(3.2%) / 10,000超 12件 / 100,000超 5件
  （ブルドーザ 622,080、小型バックホウ運転 548,352 など機械運転・単価表型が中心）
  → `計測_DB無作為500工種の縮退発動状況.csv`。gen2 だけが超える 43 型は 1件（32-3203）。
- 副産物: 32-5675「えい航費:運転費」で `decimal.ConversionSyntax` 例外（別件）。

## 方針（ユーザ決定 2026-09-02）

> 普通サイズの歩掛でこのロジックがあてられれば良い。オーバースペックの歩掛は「出せない」と返す。

## 対処（v1.2.1）

1. `step3_csv/generate_csv.py` `_build_combos`: 縮退を廃止。上限超は `CombinationExplosionError`
   「この歩掛は条件の組合せが多すぎるため、本ツールでは生成できません（組合せ N 件／上限 M 件）」。
2. `MAX_FULL_COMBOS` 1,000 → **3,000**（43=1,200 を全組合せに戻す。消波ブロック=4,096〜16,384 は生成不可）。
3. `gen_gjoken.py` `analyze`: 網羅性補完(gen2)だけが上限超なら補完を破棄し gen の結果を使う。
4. `webapp/service.py`: この例外は例外クラス名を付けず、そのまま利用者向け文として表示。
5. `webapp/test_explosion_guard.py` を新方針に書き換え（上限超→エラー／43 実データで gen2 破棄と既定上限の全組合せを確認）。
