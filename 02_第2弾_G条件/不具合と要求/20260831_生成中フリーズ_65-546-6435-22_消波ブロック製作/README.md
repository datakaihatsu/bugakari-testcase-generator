# 不具合: 「生成中」のまま固まる（65-546-6435-22 消波ブロック製作）

- 発生日: 2026-08-31（報告: imoo）
- 症状: ①G条件生成で Gaia9キー `65-546-6435-22`（歩掛キー `6435-36`・
  消波ブロック製作(個)・質問数227）を実行すると「生成中」のまま返らない。
  サーバプロセスがCPU1コア100%で回り続ける。
- 対象版: v1.1.1 以前

## 原因

無限ループではなく **組合せ爆発**。①は内部でTC生成エンジン
（`step3_csv/generate_csv.py` の `generate()`）を実行しており、
新規工種モードの「全選択肢網羅」で vary 軸が27本立ち、直積が
**1,048,576通り（2^14×4^3）** になった。1組合せごとにフロー走査
（この工種は1回0.3秒超）を行うため、完走まで数日オーダー。

悪化要因: 同名質問「使用鉄筋の単位選択」がフロー上の9箇所に独立コピーで
存在し、それぞれ独立軸として扱われた（これだけで 2^9=512倍）。
実際には工種全体で1回選ぶ条件であり、「1箇所目=t・2箇所目=m」のような
組合せは実在しない。

## 対処（v1.1.2・3段構え）

1. **軸統合**（`generate_csv.py _build_combos`）:
   質問名+選択肢表示列が完全一致する軸を「実体同一」とみなし連動化。
   6435-36 では ×9 → 1軸になり 4,096通りまで減少。
2. **直積上限ガード**: 直積件数を材料化前に計算し、`MAX_FULL_COMBOS`
   （1,000件）超過時は「基準combo+1軸ずつ変更」方式に自動縮退。
   全選択肢が最低1回選ばれるため、到達質問・選択肢の網羅
   （=G条件表の内容）は直積と同じ。6435-36 は16〜18comboで完走（約4秒）。
3. **最終防壁**: 想定外のパターンでも固まらないよう、
   - 縮退後も上限超過 → `CombinationExplosionError` を即時返却
   - webapp のリクエストに時間上限（`gen_timeout_sec`、既定300秒。
     `engine/flow_walker.py` の walk() 冒頭で検査）→ 超過で
     `GenerationTimeout` をUIにエラー表示し、スレッド/CPUを解放。
     CLI・回帰テストは上限未設定のまま（挙動不変）。

## 検証

- `65-546-6435-22` ①: 4.1秒で完走。G条件32列・注45件、
  「使用鉄筋の単位選択」は1列に集約。
- 同 ③新規歩掛経路: 1.4秒・TC53件・注45/45反映。
- 回帰テスト（`02_第2弾_G条件/regression/run_regression.py`）: **全工種完全一致**
  （既存工種は直積が上限内のため出力不変）。
- webapp テスト 64件（新規 `test_explosion_guard.py` 9件含む）全合格。

## 追記（2026-09-02・v1.2.1）: 対処2「縮退」は廃止

上記 2.（直積上限超で「基準+1軸ずつ変更」方式に縮退）は **v1.2.1 で廃止**した。
縮退サンプルでは各非基準選択肢が combo 1件にしか現れず、G条件表の(注)
「Gx=v を選ぶと Gy は入力不要」を 1 サンプルから帰納してしまい、実際には必要な条件を
「不要」と誤記する（43 捨石本均し で実証。全組合せなら回帰ベースラインと完全一致）。
列・選択肢の網羅は保たれるため劣化チェックでは検知できない。

現行の扱い: 上限（実測に基づき 3,000）超の歩掛は `CombinationExplosionError` で
「この歩掛は条件の組合せが多すぎるため、本ツールでは生成できません」と返す。
本件の 65-546-6435-22（軸統合後 4,096〜16,384件）は **生成不可**の扱いになる
（ユーザ決定: 普通サイズの歩掛が正しく出ることを優先し、オーバースペックは出せないと返す）。
詳細は `../20260902_縮退による(注)の劣化_43捨石本均し/README.md`。
