> 詳細は `docs/精度検証フェーズ_工種管理.md` の【#99 期待値列＋B-22タブ拡張】を参照。

- **期待値列を「代価表に計上される変数」から特定 (generate_csv._daika_output_s)**:
  従来は期待値列を `S\d+` 名の変数に限定していたが、代価表に上がる変数はS始まりとは限らない
  (#99: 代価表5行目 D5R=**S_ZR**)。出力行(DaikaItemCD有)の数量率(SuryoRitsuLink)を辿り、
  **式が単一変数ならその実体名**(S名問わず: S1/S_ZR/S1' 等)、複雑式は数量率変数名(D*R)を出す。
  リンク・計上が無い構造(00等)は従来のSn番号フォールバック。

  大半の工種(00含む)は不変。フロー計上(Sitsumon105)は別系統のため本関数では出さない。
- **B-22 タブ外部条件検知 (T3, external_scenarios)**: 新規 `SitTab` の `TabJoken`
  (AutoSelectJoken と同形式の表示条件)を読み、外部変数==値で開くタブを外部変数シナリオ化する。

  表示バリアントなので、AutoSelectJoken と同じ要領で検知する。

  TabJoken 評価)済みで、O~Sep=13 → SE~P=13 → 東京都建設局タブ → S_ZR=1030 を正しく算出。
- **T1 選択列挙ドライバの除外**: AutoSelectJoken を多数(>=10)駆動する変数(例 #99 H30j1=鉄筋規格
  コード・101行駆動)は「選択肢列挙ドライバ」であり外部分岐ではない。各値でシナリオ生成すると

## ③ テストケース仕様（step3.0_テストケース.csv : 列形式)

### 設計思想

「テスト軸の値の組合せをそれぞれTC1件にする」。

vary 軸 (新規追加質問・選択肢追加/削除があった質問、業務ルールで vary 昇格した質問) の **デカルト積**で TC を列挙。
fix 軸 (UI見えるがこのバージョンで変更がない質問) は **デフォルト値で固定**して全TCで同じ値を表示。
auto 軸 (AutoSelectJoken で自動確定する質問) は **"(固定)"** 注記付きで列表示、または除外。

### 出力列構成

```
テストID, テスト区分, [軸1の列ラベル], [軸2の列ラベル], ..., 期待:S1, 期待:S2, ..., 期待:S5, 選択肢の適切さ確認
```

- 軸列: SitsumonNo 昇順
- 期待:S{N} 列: 新JSON.KeisanItem に S1〜S5 が存在するもののみ
- 「選択肢の適切さ確認」: vary軸が新規追加質問・選択肢追加の場合、テンプレ文を自動生成

### 値の決定ロジック

1. **baseline scope 構築**: vary 無しで flow_walker を走らせ、全 auto-selectable 変数を確定
2. **各TC**: baseline を起点に vary軸の変数を上書き → S1〜S5 を `KeisanHyo.value()` で計算
3. **代価表行 active 判定**: TC専用 walker を走らせ、Mesho パターン `"N=代価表X枚目Y行目"` から `(sheet, row)→value` のフラグ取得
4. **空欄判定**: `(sheet=1, row=N) → 0` のとき、S{N} 列は空欄

### グループ化ルール（テスト区分=差分 1件 = TC1件)

vary 軸を Cartesian で展開した結果がそのまま TC 件数。
（v1 旧仕様の「計算式変更全件まとめて1件」等のグルーピングは廃止。テスター操作可能な「シナリオ単位 = vary軸値の組合せ」が新基準。）

## ② テスト計画仕様（step2.0_テスト計画.csv）

### 役割

新JSON の構造を解析し、テストケースに必要な「軸」を特定して分類する。
**v1 の差分起点ロジックから、JSON 全体解析ベースに刷新。**

### 出力列

| 列名 | 内容 |
|---|---|
| 軸ID | AX-001, AX-002, ... |

| 種別 | vary / auto / fix |
| SitsumonNo | 該当する SitsumonItem.SitsumonNo |
| 列ラベル | 出力CSV列名 (auto時は末尾に "(固定)") |

| 備考 | 補足情報 |

6. **ShortCut重複排除 (重要事項②参照)**: ShortCut先も軸なら参照側を除外し1列に統合

## ★ 重要事項① AutoSelectJoken の「JSON内決定」判定（軸の可視/除外）

> 人が JSON を作成する際にも迷う複雑なロジックで、全工種で多発する。
> テストケースに「ユーザが実際に選ぶ質問」だけを列として残すための中核判定。

### 原理

選択式/参照質問の各行 (SitTabRows) は `AutoSelectJoken`（駆動変数の範囲条件）で
自動選択されうる。**その駆動変数が「JSON 内で確定する」なら、ユーザは選ばず結果が
一意に決まる＝帰結表示にすぎない**ので、テスト軸（列）から除外する。逆に駆動変数が
未確定（ユーザ入力や外部マスタ依存）なら、その質問こそがユーザの選択箇所なので残す。

### 「自動決定(除外)」の定義（最終版・2026-06-03 v2.9改訂）

判定は2段階。**(A) レベル変数を持つ質問** と **(B) 持たない質問** で分かれる:

- **(A) LevelVarName を持つ質問**: レベル変数の最終値のみで開閉が決まる。
  **最終値 1 = 閉(非表示・自動確定) / それ以外(0, 2, …) = 開(表示)**。
  AutoSelectJoken の行選択判定や行構造ヒューリスティックは可視判定に使わない (重要事項⑥)。
  レベルは TC 依存 (06 撤去 → LEVsk=1 → 閉 → "-" 表示)。

- **(B) LevelVarName を持たない質問**: AutoSelectJoken のいずれかの行が
  **駆動変数の最終値で自動選択されるなら除外**。
  - 最終値は非strict評価: 未確定変数は 0、O~Sys は環境前提値 1 をシード (重要事項⑤)
  - 範囲条件の解釈は重要事項④ (単独 MaxKigou=3 は「==」)
  - **出所(Value/Expression)の有無は問わない (v2.9 で要件撤廃)**。自由な外部変数でも
    既定値 0 が行を選べば製品側で自動確定し UI に出ない
    (例: 07 材料補正区分 ZHK=0 → Row「数量に補正」(==0) → 除外)。
    0 がどの行も選ばなければユーザ選択質問として表示
    (例: 01 作業船 A3、02 数量適用区分 RFG/NFG/SFG、07 施工規模 F)。
  - 04 被災地補正: Q~j32=1 → 行成立 → **除外** / 04 道路維持: F~BIG=1.0 → どの行も
    不成立 → **表示** (計算式を持っていても除外しない)

### 具体例

| 工種 | 質問 | 駆動変数 | 判定 | 結果 |
|---|---|---|---|---|
| 01 | 作業船の選択(No15) | A3 | 未確定(外部マスタ) | **残す**(ユーザ選択) |
| 02 | 積算区分(No136/149) | Nfg2 | 確定(走査で解決) | 除外(帰結表示) |
| 02 | 数量適用区分(No120/126/154) | RFG/NFG/SFG | 未確定 | **残す** |
| 03 | 省庁区分(No13) | SF | 確定(KeisanItem定数1.0) | 除外 |
| 03 | 資料区分(No31) | SFK2 | 確定(走査で解決) | 除外 |
| 03 | 空気圧縮機延運転時間(No3) | (AutoSelect無し) | 数値入力 | **残す** |
| 04 | 道路維持補正(No2) | F~BIG=1.0 | 出所あり・**行を選ばない** | **残す** |
| 04 | 被災地補正(No1) | Q~j32=1 | 出所あり・Row4を選ぶ | 除外(外部変数で開く=将来課題) |

### JSON 単独の限界（将来課題）

JSON 外から変数を代入して初めて開く質問（例: 04 被災地補正＝発注者マスタで `Q~Did`/`Q~shk`
を制御）は、JSON 単独では「確定」扱いになり、その経路のテストは生成できない。
→ **外部変数注入によるテスト生成は将来課題**。

## ★ 重要事項② ShortCut（参照質問）の扱い

> ShortCut も今後の工種で多発する。同一質問が別ルートに参照配置されるパターン。

### 原理

`SitsumonItem.ShortCutSitsumonNo` を持つ質問は、**別の質問(ShortCut先)を別フロールートに
置いた参照**。自前の Sitsumon019(選択肢)を持たず、表示は参照先の値になる。

### 判定ルール

1. **UI可視は参照先で判定**: ShortCut元の可視/除外は、ShortCut先の質問を再帰的に
   UI可視判定して決める（2段以上のチェーンは想定外として除外）。
2. **自動決定判定も参照先で**: 駆動変数(重要事項①)は ShortCut先の AutoSelectJoken から取る。
3. **重複排除**: ShortCut先が**同じく軸として出る**場合、ShortCut元（参照側）は
   同一質問の重複なので除外し、**1列に統合**する。
   - 例: 03 Sit37(クーリングタワー延運転時間, ShortCut→Sit4) は、Sit4 も軸なので除外。
   - 注: 02 の数量適用区分(120/126/154)は ShortCut先(52/55/66)が軸でないため重複せず残す。

### 注意（番号で別物と誤判定しない）

step1 差分は SitsumonNo で突合する（正しい）。一方 step3 の列はSitsumonNoが異なると
別列になるため、ShortCut元と先(例: Sit37 と Sit4)が**通るルートは違うが同一質問**なのに
並列の2列として出てしまう。重複排除はこれを1列に束ねる。

### 判定ルール（追加: フロー走査でのShortCut処理 / B-21・2026-06-18）

4. **行選択・変数伝播・分岐も参照先で（flow_walker）**: ShortCut元は自前の Sitsumon019 を
   持たないため、`flow_walker` は従来この質問を「選択行なし」として無視し、**SitCols VarName の
   変数を伝播せず・Bunki遷移も既定(cb[0])**にしていた。これは下流の自動確定を壊す
   （#30: スライドセントルの規格(本坑用)→SBK=1 が伝播されず、施工歩掛が誤って表示された）。
   → `flow_walker._resolve_s019(sitsumon_no)`（自身に無ければ ShortCutSitsumonNo を解決し
   参照先 s019 を返す）を新設し、**行選択(`_choose_row`)・変数伝播(`_apply_row_vars`の
   active_tab/セル値)・分岐遷移(`_bunki_next_box`)・DefaultRowID探索**をすべて参照先で行う。
   これで ShortCut質問もユーザ選択質問と同じく変数を scope へ伝播し、下流の AutoSelectJoken が

## ★ 重要事項③ 複数パネルフローと「フロー切替」(2026-06-03)

> フローは1枚とは限らない(06: 2枚, 07: 6枚)。BoxNo はパネル内ローカルなので、
> 未対応だと衝突して片方のパネルしか辿れず、テストケースが大幅欠落する。

### 構造

- `FlowItems` の各ボックスは `PanelNo` を持ち、**BoxNo はパネル内でのみ一意**。
- `FlowTitles` がパネルを定義 (`PanelNo`, `PanelMesho`)。**デフォルト(主流)フローは Panel1**。
- 主流フローから他パネルを「**フロー切替**」で呼びに行く(サブルーチン呼び出し):
  - フロー切替 = `SitsumonKind=119`、Mesho が `フロー切替:X`。
  - **X が呼び先パネルの PanelMesho と一致** (例: 06 `フロー切替:適用労務切替(山林砂防工)`
    → Panel2「適用労務切替(山林砂防工)」)。
  - 呼び先パネルを開始ボックスから処理し、そのパネルの終点(CallBox=[-1])で
    **呼び出し元(フロー切替ボックスの CallBox)へ復帰**する。
  - パネルは何枚でもありうる(復帰スタックで管理)。

### 走査アルゴリズム (flow_walker)

1. ボックスを `(PanelNo, BoxNo)` で管理 (衝突回避)。
2. 開始 = Flags=[0] のうち最小 PanelNo (=主流パネル)。
3. フロー切替で対象パネルを PanelMesho 照合で解決 → 復帰先を積んでジャンプ。
4. 終点: スタック非空なら復帰、空(主流)なら走査終了。
5. 単一パネル工種(01〜05等)は従来と同一挙動(後方互換、01/02/03【合格】維持を確認済)。

### 効果 (2026-06-03)

- 06: 訪問質問 2問→10問 (作業区分/作業内容区分/材料選択/資材計上区分/…+サブパネル労務)
- 07: 軸列 0本→7本 (作業区分/敷材料の種類/敷材料の厚さ/施工規模加算/夜間補正/材料補正/市場単価補正)

## ★ 重要事項④ AutoSelectJoken の範囲条件解釈 (2026-06-03)

### 規則

- Kigou の基本: 1=「==」 / Min側 2=「>」 / Max側 2=「<」 / Min側・Max側 3=「>=」「<=」(範囲)
- **Min側の指定が無い単独の MaxKigou=3 は「==」(一致) 判定**。範囲の上限ではなく選択値そのもの

### 根拠 (07 インターロッキングブロック工)

- 時間的制約補正区分 JIK の式は `if(SEK==2, 1, if(F1==0, -1, F1))`。**-1 は「どの行も自動選択させない」番兵値**。
  もし `<=` 解釈なら -1 <= 1 で Row「無」が常に自動選択され、質問が永遠に開かない → JSON 作者の意図と矛盾
- 施工規模 F=0 → ==1/==2 に不一致 → 質問は開く(列になる)
- 材料補正区分 ZHK=0 → Row「数量に補正」(==0) に一致 → 自動確定(列に出ない)

### 実装

- `generate_proposals._joken_selects` / `flow_walker._build_shiki` の両方で同一解釈に統一
- **★Kigou確定仕様との関係 (2026-06-22)**: BugakariDefine.cs(内部仕様書 追補2)では確定で
  **1=＜(<) / 2=≦(<=) / 3=＝(==)** だが、現エンジンは上記レガシー対応 `{1:'==', 2:'<', 3:'<='}`
  (+単独Max3==特例) のまま。全工種は実害未顕在で合格しており、**グローバル是正は#17等に波及するため
  見送り**(2026-06-22 実測: Kigou是正単独で#17が変化)。B-24改の隙間判定のみ、確定仕様の
  局所関数 `_joken_selects_spec`(1=<,2=<=,3==) を使用する。グローバル是正は将来課題。

## ★ 重要事項⑤ 環境前提値 (SekisanEnv) のシード (2026-06-03)

### 規則

- O~Sys(積算システム) は SekisanEnv 連動変数で JSON 内に値を持たないが、**実行環境では 1**
- JSON 内に Value/Expression が無い場合のみ、walker 起動時に `O~Sys=1` をシードする
- 他の SekisanEnv 変数 (O~Dat 等) は必要が確認された時点で追加する

### 根拠 (06 土のう積工)

- 購入土計上区分 `ZK = if(zk>0, zk, if(RFG>0, RFG, if(O~Sys==1, 1, if(O~Dat==1, 1, 0))))`
- 実機では O~Sys=1 → ZK=1 → Row「計上する」(==1) に自動確定し、**質問は開かない = (固定) 列**
- シード無しだと ZK=0 でどの行にも一致せず「開く質問」と誤判定する

## ★ 重要事項⑥ レベル変数を持つ質問の可視判定 (2026-06-03)

### 規則

- LevelVarName を持つ質問の開閉は**レベル変数の最終値のみ**で決まる: 1=閉(非表示・自動確定) / それ以外(0,2,…)=開
- 行構造ヒューリスティック(4行1条件・MinKigou内部分岐 A'-2)は**適用しない**
- レベルは TC 依存: 同じ質問でも選択経路でレベル値が変わり開閉が変わる
  (06 作業内容=撤去 → C=3 → LEVsk=1 → 資材計上区分は閉 → TC では "-" 表示)

### 根拠 (07)

- 資材計上区分(Sit21, LEVsk) は MinKigou 行(1.0<rsskH<1.1)を持つため、A'-2 規則で内部分岐と
  誤判定され列から消えていた。レベル変数があれば開閉はレベルで決まるので行構造判定は不要

## ★ 重要事項⑦ 出力の整形規則 (2026-06-03)

- **閉質問の "-" 表示**: レベル=1 で閉じて自動確定した質問の列は、その TC では "-"
- **同一条件 TC の畳み込み**: vary 軸が到達しない TC では確認観点を出さない。その結果、
  条件・期待値・確認観点が完全同一になった TC は 1 件に畳み、テストID を再採番
- **状態戻し回帰 TC の基底補正**: 業務ルール軸(資材計上区分等)が閉じている/到達しない combo を
  基底にせず、軸が開いている先頭 combo を基底に再ウォークする
- **選択肢削除の確認観点**: 変更理由が「選択肢削除」の vary 軸には、旧JSONとの選択肢差分から
  「削除された選択肢(…)が表示されないこと」を自動生成して付与
- **表示列の選定**: ヘッダーに「係数」を含む列(補正係数 1/1.1 等)は計算パラメータであり
  名称ではない → 表示候補から除外 (07 時間的制約が「1」表示になる問題の対策)
- **市場単価工種の期待値**: 代価表セル連動質問(Kind=105/113)で数量・単価が外部の市場単価
  マスタと連動する工種は、JSON 単独で数値期待値を計算できない → 期待:S 列は出さず
  確認観点で代替する (07)

## エンジンコンポーネント

### Expression評価器 (`expression.py`)

`source_ref/sirius/Being/Core/Expressions/Parser.cs` に準拠した Python版。

主要機能:
- Decimal 主体、`^` のみ float 計算 → 特定パターンは Decimal に戻す
- `0除算 → 0`、`負底のべき乗 → 0`
- 比較演算結果は 真=Decimal(1), 偽=Decimal(0)
- `IF(c, t, f)` / `&&` → `IF(L, R, 0)` / `||` → `IF(L, 1, R)` で AST 展開
- 識別子: 英字/`'`/`@`/`_`/`~`/Unicode 128+
- `@N` 参照は `ExternalReferenceError`
- 組込関数: ROUND / ROUNDDOWN / UPPER / IF

`KeisanHyo` クラス:
- 遅延評価 + キャッシュ + 循環参照検出
- `set_input(name, value)` でユーザ入力上書き
- `strict_undefined=True` で leaf 未確定変数を `UndefinedVariableError` 化
  (Expression 経由の未確定は緩和 = 0 で代用、leaf 直参照だけ厳格)

### Flow走査 (`flow_walker.py`)

`FlowItems` を Start から traverse。

- **Start 判定**: `FlowItemFlags=[0]`
- **真の終端**: `CallBox=[-1]` または empty
  - `FlowKind=4 (End)` でも `CallBox` が非空なら通り抜ける(中間終点パターン)
- **Bunki(分岐) の遷移**: 選択行 → CallBox インデックス(選択可能行の順位対応)
- **行選択優先順位**: vary > AutoSelectJoken真(auto) > SitTab.DefaultRowID(default) > 先頭(first)
- **変数伝搬**: 選択行の SitCol(VarName列) Cell 値で `KeisanHyo.set_input`
- **代価表行フラグ**: 訪問 Sit の `Mesho` で `"N=代価表X枚目Y行目"` をパースし `{(sheet,row): value}` を返す

## ⚠ Claude判定の暫定運用と将来の置き換え戦略

### 現状の位置づけ

①.5 乖離チェックの **機械評価で 70〜80% 一致** が現実的なライン。
残り 20〜30% の項目(曖昧表現・業務的に妥当な未検出など) について、
**現状は Claude(ローカル稼働)が会話で個別にリスク評価して補完** している。

```
[機械評価 70〜80%] + [Claudeリスク評価 残り20〜30%] = 実質100%
```

### 暫定運用であることの認識

Claude(本ツール開発で利用しているローカルClaude)による判定は **暫定運用**である。
本番運用を視野に入れた場合、以下の理由で何らかの仕組みへ置き換える必要がある:

- ローカル Claude の利用がいつまで継続できるか不明
- CI/CD 等の自動実行環境に組み込めない (会話前提のため)
- 判定結果の再現性が保証できない (同じ入力でも回答が揺れる可能性)
- 業務担当者が直接判定できる仕組みの方が望ましい

### 将来の置き換え候補

| 候補 | 仕組み | 長所 | 短所 |
|---|---|---|---|
| **A. 業務知識辞書(yaml)の蓄積** | 過去の Claude判定をパターン化し `claude_risk_judgement.yaml` に蓄積 → 機械評価時に自動適用 | 自動化済・再現性高 | 新パターンが出るたびに辞書更新が必要 |
| **B. 静的リスク判定ルール** | 「曖昧表現リスト」「妥当な未検出パターン」を yaml で持つ → 機械評価時に自動適用 | 中規模実装で済む | 業務ルール変更時に追従が要る |
| **C. 業務担当者の手動判定** | step1.5_乖離チェック.csv の「リスク評価」「コメント」列を業務担当者が記入 | 業務知識の正解性が保証 | 工数発生・属人化 |
| **D. 外部 LLM API 呼び出し** | pipeline.py が Anthropic API 等を呼び出してリスク評価 | 自動化・更新性高 | API コスト・外部依存 |

**当面の推奨**: A + B のハイブリッド。

- B (静的ルール) で大半の曖昧表現を吸収
- A (辞書蓄積) で工種固有の判定を再利用
- それでも残るケースだけ Claude or 業務担当者が手動判定 (C)

### 移行計画(概要)

1. **現在**: Claude(対話)で判定 → CSVのリスク評価列を手動更新 (本セッション)
2. **次フェーズ**: Claude判定を `claude_risk_judgement.yaml` に蓄積し、pipeline で自動適用
3. **本番フェーズ**: 蓄積された yaml を静的ルール化・属人性排除 → Claude依存をゼロに
