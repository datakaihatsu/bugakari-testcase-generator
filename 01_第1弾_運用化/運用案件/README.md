# 運用案件フォルダ（第1弾・段階別レイアウト）

第1弾の運用フローを **案件（工種の1改定）単位** で管理する。入口が時間差で2回に
分かれる（①＝改定前JSON、③＝人作成TC＋改定後JSON）ため、段階ごとにフォルダを
分離する。`工種別/`（検証・回帰コーパス）は触らない。

## 段階別フォルダ規約

```
<案件>/
  10_改定前/        ①入力 : 改定前(既存版)JSON 1本だけ置く
  20_叩き台TC/      ①出力 : step2.0 / step3.0（機械生成＝人作成の基準）
  30_人作成TC/      ②成果 : 20をコピーして人が加工 ＝ ③入力その1
  40_改定後/        ③入力 : 改定後JSON（後から到着）
  50_乖離チェック/  ③出力 : 合否＋未カバー差分
```

- 案件フォルダ名は `<番号>_<工種名>_<改定日>改定` の形を推奨（例 `00_裏込砕石工_20260401改定`）。
- `10_改定前/` と `40_改定後/` でJSONを物理的に分けるので、本数ベースのモード誤判定は起きない。

## 各段階の手順

### ① 叩き台TC生成（機械・小回収）
改定前JSON1本を新規工種モードで処理し、叩き台TCを出力する。改定後JSONには触れない。

```bash
python3 01_第1弾_運用化/run_phase1.py "01_第1弾_運用化/運用案件/<案件>"
```

→ `20_叩き台TC/step3.0_テストケース.csv` ができる。

### ② 人が加工（手作業・テストファースト維持）
`20_叩き台TC/` を `30_人作成TC/` にコピーし、人が条件選択の挿入などTCを加工する。
形式は `step3.0_テストケース.csv` と同一。テストを書く主体は人。

### ③ 乖離チェック（機械・**新規実装予定**）
`30_人作成TC/` のTCを正とし、`40_改定後/` の改定後JSONをエンジン評価した結果と
突き合わせて合否＋未カバー差分を `50_乖離チェック/` に出力する。修正方針があれば
補助ヒントに併用、無ければTC単独で成立。
（※ run_phase3 は未実装。現行 step1.5 は「修正方針↔差分」ベースのため差し替え／拡張が必要）
